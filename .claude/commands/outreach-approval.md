# 提携アウトリーチ 承認レビュー

対象: `$ARGUMENTS`（空の場合は承認待ち（pending）の全件）

## このコマンドの役割

送る前の文面を**人間が承認するための材料を揃える**のがあなたの仕事です。
承認そのものはあなたの仕事ではありません。

**絶対に守ること: `approve` / `reject` / `export` / `mark-sent` を自分で実行しないでください。**
承認は人間の行為です。あなたは所見をまとめ、実行すべきコマンドを提示して止まります。
（`list` / `brief` / `status` / `log` / `verify` の読み取り系だけを実行してよい）

## 手順

1. 全体を把握する

   ```
   node scripts/outreach-cli.mjs status
   node scripts/outreach-cli.mjs list --status pending
   node scripts/outreach-cli.mjs verify
   ```

2. 対象ごとに、ブリーフと下書き本文の両方を読む

   ```
   node scripts/outreach-cli.mjs brief --prospect-id <ID>
   ```
   ```
   outreach/drafts/<ID>.md
   ```

3. 下のチェックリストで文面を検証する。**リポジトリの実データと突き合わせて確認すること**
   （記事数・掲載枠・既存の提携実績は `content/posts/` と `lib/affiliates.ts` が正）。

4. 所見を「そのまま承認してよい／直すべき点がある」の形で報告し、
   人間が実行するコマンドを提示して終了する。

## 承認前チェックリスト

事実確認

- [ ] 記載した記事数・カテゴリ・掲載予定記事が、実際のリポジトリの内容と一致している
- [ ] PV・収益などの数値が、**実測値**として書かれている（推測・盛った数字が入っていないか）
- [ ] `【要記入】` が1つも残っていない
- [ ] 宛先の会社名・サービス名の表記が公式表記と一致している（台帳の `company` / `site` が未確認なら承認しない）
- [ ] 掲載予定として挙げた記事に、実際に `{{AFF:<key>}}` の枠がある

内容

- [ ] 相手にとっての利点が具体的（どの記事のどこに、どう載るのか）
- [ ] 守れない約束をしていない（掲載期間・成果件数・順位などの保証）
- [ ] 誇張・断定的な効果表現がない
- [ ] 長すぎない（読み手が30秒で判断できる分量か）

コンプライアンス

- [ ] 広告表記・ステマ規制への対応に触れている
- [ ] 運営者情報・プライバシーポリシーの公開に触れている
- [ ] 同じ相手に重複して送っていない（`log --prospect-id <ID>` で確認）

## 報告フォーマット

```
## <ID> <プログラム名>
判定: 承認可 / 要修正
根拠:
  - （実データと突き合わせた確認結果）
要修正の場合の具体的な直し:
  - （どの行をどう直すか）

人間が実行するコマンド:
  承認:     node scripts/outreach-cli.mjs approve --prospect-id <ID> --by "<承認者名>"
  差し戻し: node scripts/outreach-cli.mjs reject --prospect-id <ID> --by "<名前>" --reason "<理由>"
```

## 補足

- 承認は承認時の本文のSHA-256に紐づきます。承認後に1文字でも編集すると承認は自動的に失効し、
  `submit` からやり直しになります。レビュー中に文面を書き換えたときは、その旨を必ず報告してください。
- このCLIはメールを送信しません。`export` は承認済み文面を `outreach/outbox/` に書き出すだけで、
  実際の送信は人間が行います。

## メール送信について

`send` コマンドで実際にメールを送信できるようになりました。これに伴う注意点です。

- **あなた（レビュー担当）は `send` を実行してはいけません。** `approve` / `reject` / `export` と同様、
  送信は運営者本人の操作です。実行するのは読み取り系のコマンドだけにしてください。
- 承認は「本文のSHA-256」と「宛先（contact.email）」の両方に紐づきます。
  レビュー時は、台帳の `contact.email` が**公式サイトで確認された実在のアドレスか**を必ず確認してください。
  推測で入れられたアドレスは、そのまま無関係の第三者へ送信されることを意味します。
- 宛先が空欄のまま承認するのは構いません（ASPフォーム経由の相手はメールを使わないため）。
  ただしその場合、`send` は必ず失敗します。
- `channel` が `asp` の相手にメールを送ろうとしている場合は、経路の誤りとして指摘してください。
